Home

Overview

#home

Vaultwarden is a Bitwarden-compatible server written in Rust. This experimental Home Assistant app wraps the official upstream image (ghcr.io/dani-garcia/vaultwarden, Alpine variant) and exposes the upstream features: organizations, Sends, emergency access, two-factor login (TOTP, WebAuthn, Duo, YubiKey), SSO (OpenID Connect), mobile push and SMTP.

#Good to know

  • HTTPS is mandatory. The web vault and all Bitwarden clients only work over HTTPS with a matching domain.
  • No Ingress. The web vault cannot run under a sub-path, so the app listens directly on port 7277.
  • SQLite only; all data below /data/vaultwarden, cold backup.
  • After initialisation the app runs as unprivileged user vaultwarden under an AppArmor profile; secrets are passed through *_FILE from a tmpfs, not as environment variables.
Unofficial community app, not affiliated with the Vaultwarden or Bitwarden projects.

Installation

Install & First Start

#installation

#Requirements

  • A reverse proxy in front of the app (e.g. Nginx Proxy Manager) that terminates HTTPS and forwards your domain (e.g. vault.example.com) to http://<ha-host>:7277. Enable WebSocket support in the proxy.
  • Alternative: ssl: true, the app then serves HTTPS itself from /ssl (not recommended by upstream).

#Steps

  1. Open Settings → Apps → App Store, add the repository https://github.com/pol4rfuchs/ha-apps, install Vaultwarden.
  2. Set domain to the public HTTPS URL, e.g. https://vault.example.com.
  3. Generate an admin token (Argon2id hash; plain text is rejected) and paste the $argon2id$… string into admin_token. Empty = admin panel disabled: 
    docker run --rm -it ghcr.io/dani-garcia/vaultwarden:latest-alpine /vaultwarden hash
  4. Set signups_allowed: true for the first account (default is false) and start the app.
  5. Create your accounts in the web vault, then set signups_allowed back to false.

Access

Reverse Proxy, HTTPS & Access

#proxy

#Local (LAN)

The web vault needs a secure context. Over plain http://<ha-host>:7277 registration and login in the browser do not work. Two ways:

  • ssl: true: certificate and key live in /ssl, access is https://<ha-host>:7277. With a self-signed certificate confirm the browser warning.
  • Reverse proxy with a local DNS rewrite: a domain such as vault.example.com points to the HA host in your local DNS. The proxy terminates HTTPS with a valid certificate and forwards to http://<ha-host>:7277 with WebSocket support on. Set domain to https://vault.example.com.

#External (internet)

OK, but only through the reverse proxy with TLS. Never port-forward the app port 7277 directly. In addition:

  • Turn signups_allowed off as soon as the accounts exist.
  • Do not expose the admin panel (/admin) publicly: leave admin_token empty if you do not need it, or restrict /admin in the proxy to LAN or VPN.
  • Enable two-factor login for every account.

#Client IP behind a proxy

With ip_header (default X-Real-IP) Vaultwarden reads the client IP from your proxy's header; it is used for rate limits. By default the header is accepted from every non-public address (local). If the proxy has a public address or you want to narrow it down, enter the proxy IPs or CIDR ranges in ip_header_trusted_proxies. Without a proxy set ip_header: none.

Security

Security & Privacy

#security

#External services

  • push_enabled: push runs through the Bitwarden relay (external service, device metadata goes there). push_region must match the region of your keys.
  • icon_service: bitwarden redirects clients to Bitwarden; internal fetches favicons directly from the sites. disable_icon_download switches every fetch off.
  • hibp_api_key turns on leak checks at haveibeenpwned.com.

#Admin panel overrides app options

If you save settings in the admin panel (/admin), Vaultwarden writes a config.json into the data folder. Its values take precedence over the app options. At start the app warns in the log when a config.json exists. Recommendation: keep configuration in the app options and use the admin panel only for administration.

#Hardening

  • The app runs as unprivileged user vaultwarden after initialisation and is confined by an AppArmor profile.
  • Secrets (admin token, SMTP password, push key, SSO secret, Yubico, Duo, HIBP) are read via *_FILE from a tmpfs, not passed as environment variables.
  • Enable smtp_accept_invalid_certs, smtp_accept_invalid_hostnames and sso_allow_unknown_email_verification only in an emergency.
  • Values in extra_env are visible in plain text in the app configuration — use the password fields for secrets.

Data

Data, Backup & Restore

#data

All data (SQLite database, RSA keys, attachments, Sends, config.json) lives under /data/vaultwarden. The app uses SQLite exclusively.

  • backup: cold: the app is stopped briefly for a Home Assistant backup so the database is consistent.
  • The icon cache and temp files are excluded from the backup.
  • Restore: restore the backup in Home Assistant and start the app.

Troubleshooting

Known Symptoms & Fixes

#troubleshooting
SymptomLikely causeFix
Registration or login fails in the browser over http://<ha-host>:7277The web vault needs a secure context (HTTPS).Use a reverse proxy with TLS or ssl: true; set domain to the HTTPS URL.
Changes to an option have no effectA config.json written by the admin panel overrides app options.Check the log warning at start; remove the setting in the admin panel or delete config.json.
Saving in the admin panel failsFeature flags removed in Vaultwarden 1.37.4 are still listed.The app filters them at start and logs a warning; restart the app.
App stops right after start with a message about missing push or SSO valuespush_enabled needs push_installation_id and push_installation_key; sso_enabled needs sso_authority, sso_client_id and sso_client_secret.Fill in the required fields or switch the feature off; the reason is in the log.
Clients do not sync liveWebSocket not forwarded by the reverse proxy.Enable WebSocket support in the proxy; keep enable_websocket: true.
No site icons showndisable_icon_download is on (default).Set it to false if you accept the privacy trade-off.
Rate limits hit the wrong clientProxy IP not in the trusted list, or wrong ip_header.Fix ip_header / ip_header_trusted_proxies; without a proxy use none.
